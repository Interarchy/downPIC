# Feature Specification: V3 效果优化闭环

> 2026-09-22 用户体验修订：[新的侧栏流程](interaction-revision.md) 优先于下文冲突的交互描述。采用三参考图就地编辑、整体确认入库及评估结果直接编辑。

**Feature Branch**: `direction/plugin`

**Feature ID**: `002-effect-optimization`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "ArchBuddy V3：以‘图片采集、提示词构建、效果优化’三个清晰阶段组织工作流；把 V2 的提示词方案沉淀为方案库，允许用户导入外部生成的效果图，对照当前方案逐项识别偏差，选择建议并生成下一版 Prompt，同时保留上一版，形成可解释、可控制的迭代闭环。"

## Clarifications

### Session 2026-09-21

- Q: 用户能否对历史 Prompt 版本发起效果评估并继续修改？ → A: 仅当前版本可评估和优化；历史版本只读、可查看和复制。
- Q: 效果评估报告是否需要在关闭插件后继续保留？ → A: 评估报告仅在当前会话保留；只有用户采纳的建议摘要随新版 Prompt 保存。
- Q: 现有 V2 草稿第一次进入“效果优化”时，应如何建立初始 Prompt 版本？ → A: 自动把草稿当前的完整 Prompt 建立为只读的 V1 基线版本，无需额外确认或重新保存。
- Q: 用户修改提示词并再次复制后，应当形成同一方案的新版本，还是一份独立方案？ → A: 在同一方案下生成新版本；“复制”同时是明确的保存节点，版本继续关联其来源参考图。
- Q: 提示词方案及版本附带的来源参考图，应当保存为什么形式？ → A: 在插件本地保存完整原图，不上传云端；同一方案的版本复用方案级原图，不重复保存副本。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 对照方案检查生成效果 (Priority: P1)

作为建筑设计师，我希望选择一份已经构建好的提示词方案，导入使用该方案在外部工具生成的一张效果图，并按设计维度查看“符合、部分符合、偏差或无法判断”的结果，以便知道成图具体偏离了哪些设计意图，而不是只凭模糊感受反复改 Prompt。

**Why this priority**: 这是 V3 的核心新增价值，也是把 V2 的“提示词构建”推进为“生成—评估—优化”闭环的关键一步。

**Independent Test**: 选择一份至少启用了三个可观察设计维度的方案，导入一张有效生成图并发起评估；检查每个启用且可评估的维度是否恰好得到一个定性结果、观察依据和修改建议，停用维度是否未被评估。

**Acceptance Scenarios**:

1. **Given** 用户选择了一份包含有效设计意图的方案并导入一张有效生成图，**When** 用户明确发起效果评估，**Then** 系统按当前方案中已启用且可观察的维度输出逐项对照结果，并提供简短的整体结论。
2. **Given** 当前方案只启用了材料与表面、视角与构图、光线与氛围三个维度，**When** 评估完成，**Then** 结果只包含这三个维度，不评价未启用维度，也不擅自补充新的设计目标。
3. **Given** 生成图无法可靠展示某个启用维度，**When** 系统无法从图中获得足够证据，**Then** 对应项目显示“无法判断”及原因，不把猜测写成确定偏差。
4. **Given** 用户只选择或预览了生成图，**When** 用户尚未点击评估动作，**Then** 系统不发送图片、不消耗调用额度，也不生成虚构的比较结果。

### User Story 2 - 选择建议并生成下一版 Prompt (Priority: P1)

作为建筑设计师，我希望参考评估结果选择建议或直接编辑原方案，并在再次复制 Prompt 时把修改结果保存为同一方案的下一版本，以便保持设计控制权、追踪方案演变并避免系统自动覆盖已经确定的内容。

**Why this priority**: 只有把“发现偏差”连接到“可控修改”，评估才会成为真正可执行的产品闭环，而不是另一段不可操作的 AI 描述。

**Independent Test**: 在一份包含多个偏差项的评估中编辑两个方案维度，再次复制完整 Prompt；检查修改后的 Prompt 成为同一方案的新版本、上一版仍可查看，未修改维度保持不变，来源参考图关联仍然存在。

**Acceptance Scenarios**:

1. **Given** 评估结果包含多条修改建议，**When** 用户只选择其中部分建议，**Then** 系统只把所选建议列入待应用变更，未选建议保持为参考信息；用户也可以不采用建议而直接编辑原方案。
2. **Given** 用户已选择至少一条建议，**When** 用户查看变更预览，**Then** 系统明确展示受影响维度的修改前内容与修改后内容，其他维度保持不变。
3. **Given** 用户已通过采用建议或直接编辑改变基于当前版本创建的工作草稿，**When** 用户再次复制完整 Prompt，**Then** 工作草稿在同一方案下保存为下一版，上一版 Prompt 保持不可变且仍可查看。
4. **Given** 某个方案维度已锁定，**When** 一条建议试图修改该维度，**Then** 系统不自动修改；用户必须先明确解除锁定，再重新确认应用。
5. **Given** 用户没有选择任何建议，**When** 用户离开评估或重新评估，**Then** 当前方案及其 Prompt 版本保持不变。
6. **Given** 当前方案由一张或多张参考图构建，**When** 用户首次或再次复制完整 Prompt，**Then** 保存的 Prompt 版本继续关联该方案的来源参考图。

### User Story 3 - 从方案库继续工作 (Priority: P2)

作为建筑设计师，我希望在“效果优化”中看到最近保存的提示词方案，能够辨认、打开并继续一份方案，同时查看它的 Prompt 版本，以便从 V2 的构建结果自然进入 V3，而不必重新复制粘贴或寻找散落的草稿。

**Why this priority**: 方案库承担工作流衔接和连续性，但其价值依赖于已经存在的提示词方案和核心评估流程，因此排在 P2。

**Independent Test**: 保存五份不同名称和更新时间的方案，进入“效果优化”后打开任一方案、查看其当前 Prompt 与历史版本，再切换方案，确认内容不会混淆。

**Acceptance Scenarios**:

1. **Given** 用户在“提示词构建”中已有本地草稿，**When** 用户进入“效果优化”，**Then** 这些草稿以“方案”形式出现在方案库中，无需再次创建。
2. **Given** 一份 V2 草稿尚无 Prompt 版本记录，**When** 用户首次在“效果优化”中打开该草稿，**Then** 系统自动把当前完整 Prompt 建立为只读的 V1 基线，且不改变草稿模块内容。
3. **Given** 方案库存在多份方案，**When** 用户选择其中一份，**Then** 页面明确显示该方案的名称、最近更新时间、当前 Prompt 版本和可用历史版本。
4. **Given** 用户保存第六份方案，**When** 本地方案数量超过五份，**Then** 系统按既定的最近更新时间规则移出最旧方案，并在执行前向用户说明结果。
5. **Given** 一份方案已经产生多个 Prompt 版本，**When** 用户查看历史，**Then** 每个版本按时间和版本顺序可辨认，历史版本只读，当前版本有明确标识。
6. **Given** 一份方案由多张参考图构建，**When** 用户在方案库中查看该方案或任一版本，**Then** 能够查看与该方案关联的本地完整来源原图，且不同版本不会重复生成相同图片副本。
7. **Given** 旧 V2 方案只有来源元数据而没有原图字节，**When** 用户打开该方案，**Then** 系统明确显示“原图缺失”，允许用户重新选择对应参考图并执行“补图”，补图成功后该方案及后续版本复用新的方案级来源图关联。

### User Story 4 - 在三个清晰阶段间连续操作 (Priority: P2)

作为第一次使用 ArchBuddy 的建筑设计师，我希望顶部功能入口直接说明“图片采集、提示词构建、效果优化”，并且每个入口只承载对应阶段的任务，以便我不用理解“采集、意图、迭代”等抽象术语，也能知道下一步该做什么。

**Why this priority**: 清晰的信息架构降低学习成本并承载完整产品逻辑，但不阻塞单独演示核心效果评估能力。

**Independent Test**: 请未接触过产品的目标用户分别寻找“下载并分类参考图”“从参考图组合 Prompt”“检查生成图并改进 Prompt”三个任务入口，验证其无需解释即可选中正确入口。

**Acceptance Scenarios**:

1. **Given** 用户打开插件，**When** 查看顶部导航，**Then** 只看到“图片采集、提示词构建、效果优化”三个一级入口，名称、顺序和选中状态清晰。
2. **Given** 用户在“提示词构建”中完成当前方案，**When** 进入“效果优化”，**Then** 当前方案可以直接被选中继续，未确认的候选意图不会被当作已完成方案。
3. **Given** 用户只想反推或构建提示词，**When** 直接进入“提示词构建”，**Then** 无需先完成图片采集；三个阶段表达推荐流程，但不构成强制前置步骤。
4. **Given** 用户只想下载和分类图片，**When** 使用“图片采集”，**Then** 不会自动触发提示词分析或效果评估。

### User Story 5 - 从失败中安全恢复 (Priority: P2)

作为建筑设计师，我希望无效图片、网络异常、服务不可用、超时或额度限制都不会破坏已有方案和历史 Prompt，以便长流程工作不会因为一次评估失败而重来。

**Why this priority**: 可靠恢复是实际使用的必要保障，但依赖于核心评估和版本流程。

**Independent Test**: 分别模拟输入无效、超时、服务不可用和结果无法解析，确认已有方案、当前 Prompt、历史版本和用户选择均不会被空结果覆盖，并存在清晰的恢复动作。

**Acceptance Scenarios**:

1. **Given** 用户已有当前方案和历史版本，**When** 一次效果评估失败，**Then** 原方案与所有 Prompt 版本保持不变，系统提供适用的重试、换图或稍后再试动作。
2. **Given** 用户选择的文件不是受支持图片、文件为空或超过大小限制，**When** 系统校验输入，**Then** 在发送前阻止评估并说明允许的格式和大小。
3. **Given** 用户当天已达到使用上限，**When** 尝试发起评估，**Then** 系统给出简洁的不可用说明，但不展示个人或公共剩余额度数字，其他本地功能继续可用。

### Edge Cases

- 当前没有任何可用方案，或所选方案没有已启用且可评估的设计维度时，系统应引导用户返回“提示词构建”，不得发起空评估。
- 用户上传原始参考图而非生成结果图时，系统无法自动证明其来源，应以清晰文案说明应上传“根据当前 Prompt 生成的结果图”，但不阻止用户继续。
- 生成图中包含多个视角、拼贴、对比图、明显水印或大面积文字时，系统应提示评估可靠性降低，并避免把遮挡区域判断为设计偏差。
- 生成图与所选方案明显无关时，系统应给出整体不匹配提示，但仍按有证据的维度说明差异。
- 一个模块同时出现符合和偏离特征时，应使用“部分符合”，并分别说明符合部分与偏差部分。
- “参考摘要”作为评估上下文而非独立视觉指标，不得为了凑齐模块数给出无意义评分；负向约束可根据结果图中是否出现被禁止特征进行检查。
- 用户连续点击评估、切换方案或替换图片时，系统应确保结果明确归属于发起时的方案、Prompt 版本和生成图，不得把旧结果写入新方案。
- 用户可以在评估后把建议加入工作草稿并继续直接编辑；评估始终关联复制时的只读当前版本，草稿编辑不得改写该版本。生成下一版或切换方案后，旧评估结束且不得继续应用。
- 建议内容为空、与原内容相同、互相冲突或会导致模块失去有效内容时，不得直接生成新版本；系统应说明问题并允许用户调整选择。
- 用户撤销应用或离开未确认的变更预览时，不得创建 Prompt 版本或改变已保存的当前版本。
- 复制历史 Prompt 失败时，用户仍可选中文本手动复制。
- 关闭面板或替换生成图后，未明确保存的生成图和评估结果不应成为长期资产。
- 本地空间不足或来源原图无法保存时，复制到剪贴板仍应完成，但系统必须明确提示方案版本尚未完整保存，并允许用户清理方案后重试，不得静默丢失来源图关联。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 插件顶部 MUST 仅使用“图片采集”“提示词构建”“效果优化”三个一级功能名称，并按该顺序展示。
- **FR-002**: “图片采集” MUST 承载现有图片下载、分类和定位能力；使用这些能力不得自动触发提示词分析或效果评估。
- **FR-003**: “提示词构建” MUST 承载参考图分析、本图候选意图、当前方案编辑和 Prompt 预览；用户可直接进入该阶段，不得强制先完成图片采集。
- **FR-004**: “效果优化” MUST 承载方案库、生成结果图导入、逐维度效果评估、建议选择和 Prompt 版本查看。
- **FR-005**: 从“提示词构建”进入“效果优化”时，系统 MUST 保留并可选择已经保存的当前方案；本图候选意图在用户明确加入前不得成为方案内容。
- **FR-006**: 系统 MUST 把现有最多 5 份本地意图草稿视为同一批提示词方案，不得要求用户为 V3 重复迁移或重新录入；一份旧草稿首次在“效果优化”中打开且尚无版本记录时，必须自动把其当前完整 Prompt 建立为只读的 V1 基线，不要求额外确认或重新保存，也不得改变草稿模块内容。
- **FR-007**: 每份新建或已完成补图的方案 MUST 至少包含可辨认名称、当前模块内容及状态、当前完整 Prompt、最近更新时间、Prompt 版本信息，以及构建该方案时使用的一张或多张本地完整来源原图。由旧 V2 草稿迁移且无法恢复原图字节的方案可以暂时标记为“原图缺失”，但不得伪造原图或把它表示为来源完整；用户必须能够重新选择对应参考图并执行“补图”。
- **FR-008**: 方案库 MUST 在同一浏览器环境中最多保留 5 份方案；达到上限后新增方案时，必须说明将移出的最旧方案，并在用户确认后执行。
- **FR-009**: 用户 MUST 能够打开、切换和删除方案；删除方案不得删除用户已下载的图片，也不得影响其他方案或其他 CloudBase 项目数据。
- **FR-010**: 用户 MUST 先选择一份至少包含一个已启用且可评估维度的方案，才能发起效果评估。
- **FR-011**: 每次效果评估 MUST 只处理一张由用户导入的生成结果图；支持 PNG、JPEG 和 WebP，文件大小必须大于 0 且不超过 10 MB。
- **FR-012**: 系统 MUST 仅在用户明确点击评估动作并确认图片会被发送给 AI 服务后发送生成图；选择、拖入或预览图片本身不得触发处理。
- **FR-013**: 每次评估 MUST 固定关联发起时的方案、当前 Prompt 版本和生成结果图；只有当前版本可以发起评估和继续优化，历史版本只读且只能查看或复制；评估进行中切换方案或图片不得改变该关联。
- **FR-014**: 效果评估 MUST 只检查当前方案中已启用且具有可观察结果的设计维度；停用维度不得进入结果，参考摘要只作为上下文使用。
- **FR-015**: 每个被评估维度 MUST 恰好返回一个定性状态：“符合”“部分符合”“偏差”或“无法判断”。
- **FR-016**: 每个被评估维度 MUST 包含对生成图中相关现象的简短观察、与目标意图的差异说明，以及在存在可执行偏差时提供一条简洁修改建议。
- **FR-017**: 评估 MUST 基于生成图中的可见证据；证据不足时必须使用“无法判断”，不得虚构不可见材料、空间、构造或项目背景。
- **FR-018**: 对负向约束的评估 MUST 说明结果图是否出现被明确禁止的特征；未设置负向约束时不得新增假设性禁用项。
- **FR-019**: 评估结果 MUST 提供一段不替代逐项结果的整体结论，并避免使用缺乏可验证基准的精确数值总分。
- **FR-020**: 用户 MUST 能够逐条选择或取消选择修改建议，也必须能够跳过建议并直接编辑基于当前版本创建的工作草稿；任何建议都不得自动改变已保存的当前版本。
- **FR-021**: 在把建议加入工作草稿前，系统 MUST 展示每个受影响维度的当前版本内容和拟修改内容；未受影响维度必须保持不变。
- **FR-022**: 已锁定维度 MUST 拒绝自动应用建议；只有用户明确解除锁定并再次确认，建议才可修改该维度。
- **FR-023**: 用户 MUST 能够直接编辑工作草稿或编辑拟采用的建议内容；用户编辑后的草稿内容优先于系统建议，且复制前不得改写已保存的当前版本。
- **FR-024**: 只有用户通过采用建议或直接编辑使工作草稿相对当前版本产生有效变化，并再次执行完整 Prompt 的复制动作后，系统才能在同一方案下生成下一版 Prompt；没有有效变化时不得创建重复版本。
- **FR-025**: 生成下一版 Prompt MUST 复用 V2 已确定的编译规则，只包含最终启用模块的有效内容，不包含评估状态、观察、证据、来源或建议说明。
- **FR-026**: 每次成功复制一份发生有效变化的完整 Prompt 时，上一版 MUST 保持不可变且可查看；新版本在同一方案下成为当前版本，不得另建一份无关方案。
- **FR-027**: 每份方案 MUST 最多保留最近 5 个 Prompt 文本版本；生成第 6 个版本时移出最旧历史版本，但必须始终保留当前版本和紧邻的上一版。
- **FR-028**: 每个 Prompt 版本 MUST 包含方案标识、版本顺序、生成时间、完整 Prompt 文本、来源参考图关联，以及本次采用的建议或用户直接修改的非敏感摘要；历史版本不得被直接覆盖。
- **FR-029**: 查看、复制、选择建议、编辑拟修改内容和编译新 Prompt MUST 不产生新的效果评估调用；只有明确发起评估才消耗一次调用额度。
- **FR-030**: 效果评估 MUST 沿用已确定的使用边界：每个匿名安装每日最多 20 次，整个 ArchBuddy 每日最多 200 次；常规界面不得展示精确剩余次数。
- **FR-031**: 评估失败 MUST 区分至少以下用户可理解的类别：输入无效、网络不可用、处理超时、服务暂不可用、使用上限已到、结果无法解析。
- **FR-032**: 任一评估失败或取消 MUST 保留原方案、当前 Prompt 和全部历史版本，且不得创建空版本或部分版本。
- **FR-033**: 工作草稿、生成结果图和完整评估报告 MUST 只用于当前评估会话，不得作为用户资产长期保存；用户切换方案、替换图片、关闭当前工作或清除会话后，系统不得继续展示不再属于当前上下文的草稿、图片或报告。只有已提交 PromptVersion 及用户实际采纳的非敏感建议摘要可以长期保存在插件本地。
- **FR-034**: 方案、Prompt 版本和本地评估工作状态 MUST 仅归属于当前浏览器中的 ArchBuddy；不得与同一 CloudBase 环境内其他项目的数据空间混用。
- **FR-035**: 当前本地 V3 MVP MUST NOT 发送新的 V3 行为统计事件；“评估开始、评估成功或失败、建议应用、Prompt 新版本”仅保留为未来事件名称。后续若另行启用，必须先完成 CloudBase 资源登记和验证，且事件 MUST NOT 包含图片、Prompt 正文、方案或模块正文、自定义文字、本地路径、网页地址或直接身份信息，并继续遵守 30 天保留上限。
- **FR-036**: 无论用户是否曾同意 V2 的最小化匿名行为统计，当前 V3 核心流程 MUST 在不发送新增 V3 行为事件的情况下完整可用；未来启用后，用户未同意或撤回统计同意时仍不得记录这些事件。
- **FR-037**: V3 默认输出语言 MUST 为中文；导航、状态、错误和主要操作文案应直接、具体，核心按钮文案 SHOULD 控制在四个汉字以内。
- **FR-038**: 在新增任何云端数据、日志、密钥、统计或额度资源前，MUST 按 ArchBuddy 项目和运行阶段登记并隔离；本规格不得授权修改其他项目资源或共享环境的全局配置。
- **FR-039**: 除 FR-007 明确允许的旧 V2“原图缺失”状态外，来源参考图 MUST 以完整原图形式保存在插件本地，不得上传或同步到云端；图片作为方案级资产保存一次，同一方案的多个 Prompt 版本必须复用该资产关联，不得为每个版本重复保存图片副本。补图操作必须写入或恢复方案级资产，不得为单个版本另存副本。
- **FR-040**: 如果本地空间不足或来源原图保存失败，系统 MUST 明确区分“已复制到剪贴板”和“方案版本未完整保存”两种结果，并提供清理方案后重试的动作；旧方案原图缺失时必须提供“补图”入口，不得把缺少来源图的版本静默标记为来源完整。

### Key Entities *(include if feature involves data)*

- **PromptScheme（提示词方案）**: 从 V2 意图草稿演进而来的工作单元，包含名称、启用的设计维度、模块状态、来源参考图关联、当前 Prompt、最近更新时间和版本集合；同一浏览器最多保留 5 份。
- **PromptVersion（Prompt 版本）**: 某个方案在用户复制完整 Prompt 时形成的只读文本快照；V1 可由旧草稿当前 Prompt 在首次进入效果优化时自动建立，后续版本在用户完成有效修改并再次复制时建立。每个版本包含版本顺序、生成时间、完整 Prompt、来源参考图关联和本次修改的非敏感摘要；每份方案最多保留最近 5 个版本。
- **SourceReference（来源参考图）**: 构建提示词方案时使用的一张或多张完整参考原图；作为方案级本地资产保存一次，由该方案的 Prompt 版本共同引用，不上传或同步到云端。
- **GeneratedResult（生成结果）**: 用户从外部图像生成工具导入、用于一次效果评估的单张图片；只在当前会话中使用，不作为长期资产保存。
- **Evaluation（效果评估）**: 固定关联一个 PromptScheme、当前 PromptVersion 和一个 GeneratedResult 的会话期对照结果，包含整体结论和多个维度评估项；完整报告不进入长期方案历史。
- **DimensionFinding（维度评估项）**: 针对一个已启用且可观察设计维度的评估，包含定性状态、可见观察、差异说明和可选修改建议。
- **RevisionSuggestion（修改建议）**: 从某个维度评估产生、可由用户选择和编辑的拟变更；只有经过变更预览和明确确认后才能写入工作草稿，不得直接改写已保存的当前版本。
- **WorkingDraft（工作草稿）**: 从已保存的当前 Prompt 版本派生的会话期可编辑状态，可接收用户直接修改或所选建议；再次复制前不改变当前版本，复制并提交成功后成为同一方案的下一版。它不作为长期方案资产保存，切换方案或会话结束时按提示丢弃。
- **RevisionPreview（变更预览）**: 用户把建议加入工作草稿前的临时对照，展示所选建议会如何修改对应模块；取消或离开时不产生版本。

## Success Criteria *(mandatory)*

### Measurable Outcomes

以下指标分为两类：SC-002、SC-003、SC-004、SC-005、SC-006、SC-007、SC-008、SC-011 是实现行为目标，可在 MVP 的人工演示中核对；SC-001、SC-009、SC-010 是实现后的产品验证指标，未执行并留存证据前不得宣称已经达成。

- **SC-001**: 在 5 名首次使用 ArchBuddy 的目标建筑设计师中，至少 4 人能够在无口头指导下为“下载分类参考图、从参考图构建 Prompt、检查成图并优化 Prompt”三个任务选择正确的一级入口。
- **SC-002**: 用户从一份已有方案和一张有效生成图开始，最多通过“选择方案、导入图片、开始评估”3 个主要动作进入逐维度评估结果。
- **SC-003**: 对预设方案进行人工验收时，100% 的已启用且可评估维度在结果中恰好出现一次，停用维度出现次数为 0，参考摘要不会被当作独立评分项。
- **SC-004**: 在建议应用和直接编辑验收用例中，100% 的未选建议、未涉及维度和锁定维度保持不变；用户选择的建议或直接修改准确写入对应维度。
- **SC-005**: 每次复制发生有效变化的完整 Prompt 均在同一方案下产生可辨认的新版本，且上一版文本和来源参考图关联在 100% 的验收用例中仍可查看。
- **SC-006**: 在输入无效、网络中断、超时、服务不可用、使用上限和结果异常的模拟场景中，原方案及其 Prompt 版本丢失或被覆盖的次数为 0。
- **SC-007**: 除明确点击“开始分析”或“开始评估”外，选择图片、切换页面、编辑方案、选择建议、查看版本和复制 Prompt 导致的额外 AI 调用次数为 0。
- **SC-008**: 生成结果图在替换图片、清除当前评估或关闭对应会话后不再作为长期资产出现；行为事件中图片、Prompt 和自定义正文的记录次数为 0。
- **SC-009**: 在 5–8 名目标用户的可用性测试中，至少 80% 能够解释一条评估结论对应的原方案维度，并独立完成“评估 → 选择建议 → 预览变更 → 生成下一版 Prompt”。
- **SC-010**: 至少 80% 的目标用户认为逐维度“状态 + 偏差 + 建议”比直接重写整段 Prompt 更容易理解改动原因，并能准确指出哪些内容由自己选择后进入新版本。
- **SC-011**: 在正常网络和服务条件下，90% 的有效效果评估在用户明确发起后 60 秒内返回可审阅结果，且发起后 1 秒内显示明确的处理中状态。

## Assumptions

- V3 仍面向建筑设计师和建筑视觉工作者，默认使用中文，不扩展为跨行业通用产品。
- 图片生成继续发生在 ArchBuddy 之外；用户自行把当前 Prompt 交给外部生成工具，再把一张结果图导回 ArchBuddy。
- 每次效果评估只处理一张生成图，并以所选方案的当前 Prompt 版本为唯一对照基准；历史版本只读，不可作为新评估或优化的起点。多图排序、批量评估和 A/B 对比留到后续阶段。
- V2 的最近 5 份意图草稿原位升级为方案库；能够取得原图字节的方案在插件本地保留完整来源原图，版本复用方案级图片关联。旧草稿无法取得原图时明确标记为“原图缺失”并允许补图，不建立账户、云端素材库、跨设备同步或团队协作。
- 每份方案最多保留最近 5 个 Prompt 文本版本，以满足 MVP 的回看需要并控制本地信息复杂度。
- 效果评估与参考图分析共用 ArchBuddy 已确定的个人每日 20 次、产品每日 200 次调用边界；编辑和版本操作不计入调用次数。
- 生成结果图和完整评估报告只用于当前会话，不长期保存；来源参考图作为方案级完整原图保存在插件本地，方案、Prompt 版本和随版本保存的已采纳建议摘要同样只保存在本地。
- “参考摘要”用于帮助理解整体目标，不作为独立视觉评分项；负向约束只有在当前方案明确设置时才参与检查。
- V3 的方案比较基于可见结果和用户已表达意图，提供定性判断而非宣称客观审美分数。
- 当前阶段以本地 MVP 和核心路径为目标，不要求立即部署 V2 或 V3；后续云端实现和部署仍需通过 CloudBase 多项目隔离检查。
- 本规格关于“导入生成结果并优化 Prompt”的 V3 决策取代 V2 规格中将该能力暂列为更晚阶段的旧假设；V2 已实现能力本身不变。

## Out of Scope

- 在插件内直接调用图像生成模型、替用户提交生成任务或管理外部生成平台账户。
- 同时导入多张生成图进行排名、A/B 对比、批量打分或自动选择最佳结果。
- 自动应用全部建议、无人确认地覆盖方案，或根据评估结果自动循环生成。
- 缺乏明确评测基准的百分制总分、跨项目排行榜或“审美质量”绝对评分。
- 云端图片素材库、生成结果长期归档、账户体系、跨设备同步和多人协作。
- 分支式版本树、任意版本合并、复杂回滚和差异编辑器；MVP 只保留线性最近版本。
- 营销、电商、UI、视频或企业知识工作等跨行业版本。
- 本阶段直接部署 V2/V3、修改 CloudBase 共享环境全局配置，或新建未经登记的云端数据资源。
