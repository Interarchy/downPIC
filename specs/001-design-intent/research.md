# Phase 0 研究记录：ArchBuddy V2

## 结论 1：继续使用现有原生 Manifest V3 架构

**决定**：不引入 React、状态管理库或构建工具；继续使用 `sidepanel.mjs`、`background.mjs` 和 `shared.mjs`。

**理由**：V2 的主要复杂度是状态规则和数据契约，而不是组件规模。现有界面、消息通道、图片选择和 CloudBase 调用均可复用，引入框架会扩大迁移面并偏离 MVP。

**未采用方案**：重写为 React 或创建通用工作流引擎。它们可能改善长期维护，但本阶段没有足够收益。

## 结论 2：草稿使用 `chrome.storage.local`，当前图片继续使用会话存储

**决定**：最近 5 份草稿保存在 `chrome.storage.local`；图片选择、图片字节和当前临时结果继续保存在 `chrome.storage.session`。草稿不保存图片、缩略图或来源网址。

**理由**：Chrome 官方文档说明 `storage.local` 可跨浏览器会话持久化，默认配额约 10 MB；5 张最大 10 MB 的图片无法安全放入该区域。只保存结构化文本和状态既可恢复工作，又降低隐私风险。`storage.session` 适合重启扩展服务工作线程时保留当前会话数据，且不会长期落盘。

**未采用方案**：把图片编码后写入草稿，或使用 IndexedDB 建立图片库。前者容易超额，后者扩大本阶段范围。

**参考**：[Chrome Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage)

## 结论 3：模型输出采用可恢复的标签协议，服务端输出结构化 JSON

**决定**：模型文本继续使用固定 `【模块标题】` 块，并在块内输出“内容、证据、置信度”；服务端解析为固定 11 模块 JSON。

**理由**：现有解析器已能从部分文本恢复有效段落。严格要求模型返回一整段 JSON 时，一旦截断，整个响应更容易不可解析。标签协议只需扩充现有逻辑，符合最小改动原则。

**未采用方案**：直接把模型 JSON 原样透传给扩展；在客户端根据自然语言猜测证据和置信度。前者对截断敏感，后者会让业务规则分散且难以保证一致。

## 结论 4：分析接口采用单一 V2 契约

**决定**：`/api/analyze` 与扩展在同一 V2 发布批次切换为 `contractVersion: 2` 和 `modules`，不保留旧响应字段。

**理由**：项目当前仍处于 MVP 与商店审核阶段，项目宪法明确禁止面向未来的多阶段兼容层。单一契约减少分支和双源数据，部署时通过同一发布窗口协调前后端。

**未采用方案**：同时返回 `sections` 与 `modules`，或新建 `/api/v2/analyze`。两者都会形成不必要的兼容路径或重复认证、配额和错误处理。

## 结论 5：提示词只由本地确定性编译器生成

**决定**：固定准则与启用模块在浏览器本地按固定顺序拼接。证据、置信度、来源和状态永不进入提示词。

**理由**：编辑或开关模块不应再次计费或等待模型；确定性编译也能保证用户看到的内容与复制内容一致。

**未采用方案**：每次编辑后调用 LLM 重写提示词。它会增加费用、延迟和不可控变化。

## 结论 6：重新分析由客户端按模块键合并

**决定**：服务端每次返回一份完整新建议；扩展根据固定模块键保留 `reviewState=modified`、`locked=true` 或已停用模块，仅替换未修改 AI 建议，并在新旧值变化时设置 `changed`。

**理由**：服务端无需接收旧提示词或用户文本，既减少敏感内容上传，又让合并规则保持可见和确定。

**未采用方案**：把当前草稿上传给模型，请模型决定保留内容。该方案会上传用户自定义文本，并让合并不可预测。

## 结论 7：行为统计单独选择加入，采用最小事件白名单

**决定**：统计开关默认关闭；只发送事件名、结果类别、客户端事件 ID 和客户端时间。服务端补充固定项目、阶段、匿名身份摘要、接收时间和 `expiresAt`。不允许任意属性对象。启用前必须同步更新扩展、公开站点和 Chrome Web Store 中所有“当前不收集用户活动”的披露，同意入口直接链接更新后的政策。

**理由**：产品只需要验证核心漏斗，不需要收集图片、网址、提示词或自由文本。字段白名单可在服务端阻止客户端误传敏感内容。

**未采用方案**：使用通用埋点 SDK 或记录完整交互负载。它们会扩大依赖、数据面和审核风险。

## 结论 8：事件集合必须先完成隔离登记和 TTL 验证

**决定**：计划集合名为 `archbuddy_dev_events`，仅由服务端写入，保留期最多 30 天。生产统计只有在 `docs/CLOUDBASE_PROJECT_ISOLATION.md` 登记集合与 `ARCHBUDDY_ANALYTICS_ENABLED`、权限验证和 `expiresAt` TTL 验证完成后才能启用。现有 CloudBase store 只初始化一次，并同时提供 quota 与 event writer。

**理由**：共享 CloudBase 环境还会承载其他项目。前缀只能帮助识别，不能代替权限和生命周期控制。CloudBase Node SDK 支持通过集合、文档和查询 API 写入与管理数据，但集合权限和 TTL 仍需在目标环境中单独配置并留证。

**未采用方案**：复用配额集合、为统计重复初始化 CloudBase SDK、记录到日志或仅依靠名称前缀。它们会混淆数据用途、制造连接与配置双源，且无法满足 30 天保留边界。

**参考**：[CloudBase Node SDK 数据库使用说明](https://docs.cloudbase.net/cloud-function/resource-integration/cloudbase)

## 结论 9：不新增 Chrome 权限

**决定**：V2 使用现有 `storage`、`activeTab`、`scripting`、`sidePanel`、`downloads` 和既有主机权限；不申请新的权限。

**理由**：结构化编辑、草稿和统计均可在现有权限内完成。减少权限是降低商店审核风险最直接的方式。

**未采用方案**：增加身份、历史记录、无限存储或后台常驻权限。V2 不需要这些能力。

## 结论 10：验证范围遵循项目宪法

**决定**：只做语法、Manifest JSON 和商店包静态检查，并提供人工核心路径演示步骤；不新增或运行自动化测试。

**理由**：当前项目明确定位为复杂产品的 MVP 演示，目标是快速验证核心工作流。

**未采用方案**：搭建单元、集成或端到端测试框架。它们不属于本阶段交付。
