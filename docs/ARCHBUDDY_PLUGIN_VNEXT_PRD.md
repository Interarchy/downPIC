## 0. 文档目的

本 PRD 将 ArchBuddy 从“一键下载 + 单图反推提示词”两个相邻工具，升级为一条连续的 AI 产品工作流：

**参考采集 → AI 理解 → 设计语义结构化 → 人工选择与编辑 → 可控 Prompt → 结果对比 → 反馈优化**

本文同时吸收两类输入：

1. 建筑师真实工作流：参考案例研究与 AI 视觉表达之间存在断层。
2. 通用 AI 产品逻辑：把人类模糊的“我想要这种感觉”转化为机器可理解、组合、执行和评估的结构化意图。

本文不会把远期设想写成已完成能力。所有内容明确分为：

- **Current**：0.3.1 已实现并验证。
- **Next / V2**：下一轮优先实现与验证。
- **Later / V3–V4**：验证 V2 后再决策。

本次仅形成产品设计初稿，不涉及 CloudBase 资源、数据、身份、密钥、日志、统计或预算变更。

## 1. 产品结论

### 1.1 一句话定位

**ArchBuddy 是面向建筑、室内与景观设计师的 AI 视觉意图助手，帮助用户把网络参考图转化为可编辑、可组合、可执行的设计语言。**

### 1.2 用户价值

用户不必从一张参考图重新人工判断“喜欢它的什么”，也不必面对一整段难以修改的 Prompt。ArchBuddy 将可见视觉特征拆成建筑师熟悉的维度，让用户保留判断权，并把确认后的设计意图编译成可用于外部生图工具的 Prompt。

### 1.3 核心产品母题

> 如何将人类模糊的参考与意图，转化为机器可以理解、组合、执行和评估的结构化信息。

### 1.4 产品边界

ArchBuddy 聚焦建筑方案过程中的两段工作：

- 参考案例研究：找到、保存、理解和组织参考图。
- AI 视觉表达：形成设计意图、编写 Prompt、检查生成结果并迭代。

ArchBuddy **不是**：

- 建筑设计全过程平台。
- 自动替用户完成方案判断的“AI 建筑师”。
- BIM、CAD、参数化建模或施工设计工具。
- 图片版权判断或访问控制绕过工具。
- 下一版本就覆盖营销、电商、UI、视频与企业知识的通用平台。

跨行业迁移是产品能力的抽象与作品集表达，不是当前开发范围。

## 2. 背景与问题

### 2.1 建筑师的真实工作流

建筑方案阶段可以简化为：

1. 理解项目信息与约束。
2. 分析场地与核心问题。
3. 判断设计方向。
4. 搜集和研究参考案例。
5. 形成并迭代方案。
6. 制作视觉表达并根据结果反推方案。

实际过程并非线性，而是在“方向判断—找参考—改方案—做效果—发现问题”之间反复循环。ArchBuddy 的切入口是第 4 与第 6 阶段之间的断层。

### 2.2 当前版本解决了什么

| 已有能力 | 已解决问题 |
| --- | --- |
| 网页图片悬浮保存 | 减少右键另存、选择目录和反复命名 |
| 项目类型与网页标题目录 | 形成最基础的本地归档结构 |
| 原图读取与截图回退 | 提高不同网页上的图片可用性 |
| 单图反推中文结构化提示词 | 降低从视觉参考到 Prompt 的表达门槛 |
| CloudBase 匿名会话 | 用户无需配置模型 Key 或注册登录 |
| 服务端额度与隐私确认 | 控制成本，并保证图片仅在用户主动确认后发送 |

### 2.3 当前版本的核心缺口

“保存图片”与“反推提示词”仍然是两条独立路径：

```text
保存图片 → 文件夹

参考图 → 一整段 Prompt → 复制到其他工具
```

主要问题：

1. 下载后的图片没有成为可继续理解和调用的设计资产。
2. AI 输出虽然分段，但本质上仍是一整份文本，不方便局部调整。
3. 系统无法记录用户究竟选择了参考图中的哪一部分。
4. 多张参考图之间不能分工组合。
5. 用户拿到生成结果后，无法定位“哪里没有符合原始意图”。
6. 产品价值仍容易被理解为“下载插件 + 视觉模型调用”。

## 3. 目标用户与核心任务

### 3.1 主要用户

- 建筑设计师，尤其是方案阶段与视觉表达阶段人员。
- 建筑可视化设计师。
- 室内与景观设计师作为相邻验证用户。

首轮不以普通 AI 绘画爱好者为主要用户，避免设计语义被泛化。

### 3.2 核心 Job to Be Done

> 当我看到一张或多张喜欢的设计参考图时，我希望快速弄清楚自己喜欢哪些可迁移特征，并把这些特征组合成可编辑、可执行的生成意图，以便更稳定地得到符合目标的效果图，而不是反复重写整段 Prompt。

### 3.3 关键场景

#### 场景 A：单图理解

用户看到一张参考图，希望提取体量、立面、材料、光线与氛围，但不想照搬项目本身。

#### 场景 B：局部修改

AI 已生成 Prompt，用户只想把“高反射玻璃”改为“低反射高透玻璃”，其他模块不变。

#### 场景 C：多图组合

用户喜欢 A 图的体量、B 图的材料、C 图的景观与 D 图的光线，希望组合成一份明确的视觉意图。

#### 场景 D：结果纠偏

用户已在外部工具生成效果图，希望知道结果在哪些维度偏离目标，并只修改对应意图模块。

## 4. 产品原则

### 4.1 AI 提建议，人做决定

- AI 提取可见证据、建议分类与候选描述。
- 用户决定保留、删除、修改、锁定和组合哪些内容。
- 用户修改后的字段优先级高于 AI 结果，普通重新分析不得覆盖。

### 4.2 结构先于长文本

Prompt 是结构化意图的编译结果，不是唯一资产。系统必须先保存字段与来源，再生成可复制文本。

### 4.3 可见证据优先

不猜测项目名称、建筑师、地点、不可见空间、施工方式或原始模型参数。无法确定时使用宽泛但准确的描述，并标记不确定性。

### 4.4 局部可控

用户应能只修改材料、光线、镜头等单一模块，而不必重写或重新生成全部内容。

### 4.5 先闭环，后平台

先验证建筑场景中的完整小闭环，再考虑云端大素材库、直接生图、团队协作与跨行业 Schema。

### 4.6 隐私与成本显式

- 只有用户主动确认后才发送图片。
- 原图默认不持久化到 ArchBuddy 云端。
- 不在扩展中放置模型 Key。
- AI 调用遵循个人每日 20 次、ArchBuddy 每日 200 次的既有规则。
- 自动分类不得在用户不知情时批量消耗额度。

## 5. 产品能力架构

```text
Unstructured Reference
        ↓
AI Understanding
        ↓
Structured Design Representation
        ↓
Reference / Intent Workspace
        ↓
Human Selection & Composition
        ↓
Prompt Compilation
        ↓
External Generation
        ↓
Result Evaluation
        ↓
Targeted Refinement
```

对应产品层：

| 产品层 | 建筑场景中的含义 | 当前状态 |
| --- | --- | --- |
| 输入层 | 网页图片、粘贴图、拖入图、生成结果图 | 单图输入已实现 |
| 理解层 | 体量、空间、立面、材料、景观、镜头、光线、氛围 | 已有文本分项，待结构化 |
| 资产层 | 参考卡片、项目会话、来源、标签、用户修改 | 待实现 |
| 意图层 | 选择模块、锁定字段、多图分工组合 | 待实现 |
| 生成层 | Prompt 编译、复制到外部工具 | 基础复制已实现 |
| 评估层 | 目标意图与生成结果的分维度差异 | 远期 |
| 反馈层 | 根据差异生成局部修改建议和版本 | 远期 |

## 6. 版本策略

### 6.1 Current：0.3.1 Beta（已实现）

- 网页图片工具总开关。
- 图片悬浮保存与反推入口。
- 预设和自定义项目类型。
- 下载至 `下载/ArchBuddy/项目类型/网页标题/`。
- 下载后在文件夹中显示。
- 侧栏粘贴、拖入图片。
- 中文结构化提示词与固定整体生成准则。
- 用户确认后才发送图片。
- CloudBase 服务端模型调用、匿名安装会话和每日额度。
- 普通用户不显示具体剩余额度。

### 6.2 Next：V2（本 PRD 的交付重点）

**目标：把“单图反推长文本”升级为“结构化视觉理解 + 可编辑设计意图”。**

V2 必须形成以下闭环：

```text
选择参考图
→ AI 结构化理解
→ 用户审阅与局部编辑
→ 形成设计意图
→ 编译并复制 Prompt
```

### 6.3 Later：V3

- 项目级 Reference Workspace。
- 多图角色分配与设计意图组合。
- 参考模块来源追踪。

### 6.4 Later：V4

- 导入生成结果。
- 按结构化意图进行差异评估。
- 生成可解释的局部修正建议。
- Prompt 版本与迭代记录。

### 6.5 暂不承诺

- 在插件内直接调用图像生成模型。
- 当前阶段的完整素材库；后续先建设插件内本地网页素材库，云同步须单独验证和立项。
- 自动抓取网页所有图片。
- 团队协作、公开素材市场和跨设备同步。
- CAD/BIM/模型文件理解。
- 营销、电商、UI 或视频行业版本。

## 7. V2 信息结构：Design Intent Schema

V2 内部使用结构化对象，界面以设计师可理解的模块呈现。字段不是让模型机械填满；没有可见证据时允许为空。

| 模块 | 核心内容 | 说明 |
| --- | --- | --- |
| 参考摘要 | 核心视觉特征、主要参考价值 | 帮助用户快速判断这张图是否值得继续使用 |
| 场景与主体 | 场景类型、主体形态、体量关系 | 不强猜建筑功能 |
| 空间与体量 | 体块组织、虚实、退台、开敞与围合 | 建筑垂直领域重点 |
| 立面与构件 | 开窗、格栅、栏杆、幕墙、水平/竖向关系 | 描述可见形式 |
| 材料与表面 | 颜色、纹理、粗糙度、反射、透明度 | 不编造具体材料品牌或型号 |
| 景观与配景 | 植被、地形、水体、铺地、人物与家具 | 无明显内容时可为空 |
| 视角与构图 | 观察高度、方向、透视、主体位置、前中后景 | 不虚构焦距 |
| 色彩与明暗 | 主辅色、冷暖、饱和度、对比与分布 | 不提供伪精确色号 |
| 光线与氛围 | 光线方向、软硬、阴影、天气证据与氛围 | 区分可见事实和氛围概括 |
| 图像表现 | 摄影、写实可视化、拼贴、手绘、清晰度 | 不堆叠空泛质量词 |
| 负向约束 | 用户明确不希望出现的结果 | 仅由用户输入或确认，不由 AI 任意扩展 |

每个模块至少包含：

- `value`：可编辑描述。
- `source`：AI 建议或用户输入。
- `state`：建议、已确认、已修改、已锁定、已排除。
- `evidence`：可选的简短可见依据。
- `confidence`：仅用于提示不确定性，不展示伪精确百分比。

## 8. V2 功能需求

### FR-200 结构化图片分析｜P0

用户可从网页浮栏或侧栏选择一张图片发起“解析设计意图”。

验收标准：

- 发送前展示处理说明并由用户确认。
- 服务端返回符合版本化 Schema 的结构化结果，不只返回一整段散文。
- 至少返回参考摘要，以及有证据的四个分析模块。
- 不确定字段允许为空或标记“无法确定”。
- 模型格式异常时不得把半成品标为成功。
- 原有固定整体生成准则继续由代码控制，不信任模型回显。
- 网页按钮、水印和页面文字不得被当成指令。

### FR-201 设计意图卡片｜P0

分析结果以模块卡片展示，而不是只显示完整 Prompt。

验收标准：

- 用户可以展开、折叠、删除和恢复模块。
- 每个模块区分 AI 建议与用户已确认内容。
- 空模块不占用主要界面空间。
- “查看完整 Prompt”是结果视图之一，不是唯一视图。

### FR-202 模块化编辑｜P0

用户可单独修改一个模块而不影响其他模块。

验收标准：

- 编辑后标记为“用户修改”。
- 重新编译 Prompt 时立即使用修改后的内容。
- 普通重新分析不得覆盖用户修改或锁定的字段。
- 用户可恢复该模块到本次 AI 原始建议。
- 支持添加一条用户自定义描述与负向约束。

### FR-203 Prompt 编译器｜P0

系统将当前已启用的设计意图模块编译成可复制 Prompt。

验收标准：

- 固定整体生成准则位于最前。
- 后续模块按稳定顺序输出，减少重复表达。
- 删除或关闭的模块不进入 Prompt。
- 用户修改内容优先于 AI 建议。
- 支持复制完整 Prompt 和单个模块。
- 编译过程不再调用模型，不额外消耗额度。

### FR-204 本次意图草稿｜P0

用户在关闭侧栏或浏览其他网页后，可继续最近一次未完成编辑。

验收标准：

- 结构化文本与编辑状态保存在浏览器本地。
- 默认不在本地长期保存发送给模型的原始图片副本。
- 明确提供“新建意图”和“清除当前草稿”。
- 清除操作只清除 ArchBuddy 本地草稿，不删除下载目录中的图片。

### FR-205 保存与分析的关系｜P0

下载归档和 AI 分析继续是两个独立授权动作，但在界面上形成连续流程。

验收标准：

- “保存图片”不自动调用模型、不消耗额度。
- 保存成功后可继续点击“解析为设计意图”。
- 用户也可只分析、不下载。
- 已下载记录保留文件夹定位入口。
- 如果用户继续分析，意图草稿记录该图的公开来源页面和本地下载状态；不保存模型密钥或管理员凭据。

### FR-206 输出历史与版本边界｜P1

V2 至少保存最近若干次结构化意图的文本版本，便于返回查看。

验收标准：

- 每条记录显示时间、来源页面标题、项目类型和状态。
- 原图默认不随历史记录复制保存。
- 用户可删除单条本地记录。
- 首版不承诺跨设备同步。

### FR-207 失败与降级｜P0

验收标准：

- 模型不可用时，下载与分类继续可用。
- 冷启动、超时、格式错误、额度限制和图片不可读取使用不同提示。
- 结构化解析失败时不覆盖上一次有效草稿。
- 已有完整文本结果若可安全解析，可降级展示；无法满足 Schema 时明确提示重新分析。

## 9. V3 候选需求：多图组合与 Reference Workspace

V3 只有在 V2 的结构化意图确实被用户编辑和复制后才进入开发。

### FR-300 项目参考工作区｜P1

- 用户可创建一个轻量项目会话，而非云端完整素材库。
- 参考卡片记录图片来源、项目类型、AI 摘要、标签和用户确认状态。
- 下载文件仍在本地目录，浏览器只保存必要元数据。
- AI 不在后台自动批量分析所有下载图片。

### FR-301 AI 参考角色建议｜P1

AI可建议图片主要用于：体量、空间、立面、材料、景观、构图、光线、氛围或图像表现。

用户可修改角色；同一图片可以承担多个角色，但必须明确主角色。

### FR-302 多图意图组合｜P1

用户为不同模块选择不同参考图，例如：

- A 图 → 体量。
- B 图 → 立面与材料。
- C 图 → 景观。
- D 图 → 光线与氛围。

验收重点：

- 每个意图模块能追溯到参考图和用户选择。
- 冲突信息不静默拼接，系统提示用户选择或保留差异。
- 组合后仍是可编辑模块，不直接退化为不可解释的长文本。
- 单图用户不被迫进入多图流程。

## 10. V4 候选需求：比较与反馈闭环

### FR-400 导入生成结果｜P1

用户可粘贴或拖入一张外部生成结果，选择要对比的设计意图版本。

### FR-401 分维度差异评估｜P1

系统按体量、材料、景观、构图、光线、氛围等已启用模块评估。

首版不展示缺乏可靠标定的总分，使用：

- 基本一致。
- 部分一致。
- 明显偏离。
- 无法判断。

每项必须给出可见依据，并区分“参考图事实”“用户目标”和“模型判断”。

### FR-402 定向修正建议｜P1

- 只为偏离模块生成修改建议。
- 用户先审阅建议，再应用到意图草稿。
- 已锁定模块不得被自动修改。
- 保留修改前后版本，支持撤销。

### FR-403 再次生成交接｜P2

系统重新编译 Prompt，用户复制到外部生图工具。是否接入直接生图 API，依据 V4 使用数据和成本另行立项。

## 14. AI 设计与评测

### 14.1 模型职责

模型负责：

- 从可见证据提取建筑视觉语义。
- 输出受约束的结构化字段。
- 对无法判断的字段保持空值或不确定。
- V3 中识别参考角色与冲突。
- V4 中按已确认意图比较差异并提供证据。

模型不负责：

- 替用户选择最终设计方向。
- 猜测建筑功能、项目背景和不可见设计。
- 判断版权归属。
- 未经用户确认自动修改锁定意图。

### 14.2 离线评测集

建立一组经人工标注的建筑、室内与景观参考图，覆盖：

- 多种图像类型：实景摄影、写实效果图、拼贴、手绘。
- 多种场景：建筑外观、室内、公共空间、景观。
- 简单与复杂构图。
- 材料不确定、功能不确定和信息缺失样本。
- 网页水印、字幕和插件浮栏干扰样本。

### 14.3 结构化理解指标

| 指标 | 定义 |
| --- | --- |
| Schema 合法率 | 返回结果可被契约完整解析的比例 |
| 可见证据一致率 | 人工判断描述是否由图中证据支持 |
| 幻觉率 | 出现不可见项目、地点、材料型号、设计意图等内容的比例 |
| 模块有效率 | 用户保留或只做轻微编辑的模块比例 |
| 字段覆盖 | 有明显证据的关键维度是否被正确提取 |
| 重复度 | 不同模块之间是否重复堆叠同一描述 |

### 14.4 可控性指标

- 单模块修改后，其他模块是否保持不变。
- 用户锁定内容是否在重分析和优化中保持。
- Prompt 编译结果是否完整反映用户当前选择。
- 用户能否指出每段 Prompt 来自哪个模块或参考。

### 14.5 V4 对比评测

- 差异描述是否基于可见证据。
- 是否优先发现用户已启用模块中的明显偏差。
- 修改建议是否只作用于对应模块。
- 不确定时是否避免强结论。

## 15. 成功指标与验证计划

### 15.1 北极星行为

**完成一次“结构化意图确认 → Prompt 复制”的有效工作流。**

它比“完成一次图片分析”更接近产品价值，因为用户已经审阅并形成可执行意图。

### 15.2 V2 核心漏斗

```text
选择参考图
→ 发起结构化分析
→ 查看模块
→ 至少确认/修改一个模块
→ 复制编译 Prompt
```

建议指标：

- 结构化分析成功率。
- 模块审阅率。
- 模块修改率与删除率。
- Prompt 复制率。
- 从选择图片到复制 Prompt 的完成时间。
- 用户对“更容易表达我想要什么”的主观评分。

### 15.3 首轮研究方法

在没有获得用户统计授权和埋点实现前，先采用人工任务测试，不声称拥有线上行为数据。

建议招募 5–8 名建筑、室内或景观设计师，每人完成：

1. 使用一张参考图形成 Prompt。
2. 修改一个材料模块，保持其他模块不变。
3. 删除一个不希望迁移的参考特征。
4. 解释最终 Prompt 各部分来自哪里。

记录任务完成率、耗时、修改位置、误解点和访谈反馈。首轮数据用于确定正式阈值，而不是预先编造漂亮指标。

### 15.4 V2 退出条件

- 结构化结果稳定满足 Schema 契约。
- 用户能独立完成局部编辑和 Prompt 编译。
- 用户明确理解“参考图事实”与“自己的目标意图”的区别。
- 模型失败不会破坏已有草稿。
- 下载功能在 AI 服务不可用时仍正常。
- 隐私、额度和本地存储说明完成更新。
- 至少完成一轮真实用户任务测试，并据此决定是否进入 V3。

## 16. 风险与应对

| 风险 | 产品影响 | 应对 |
| --- | --- | --- |
| AI 输出结构稳定但内容空泛 | 模块看似完整却没有设计价值 | 离线样本评测、可见证据约束、用户保留率评估 |
| Schema 维度过多 | 用户审阅负担高 | 默认只展开核心模块，按证据隐藏空模块 |
| Schema 维度过少 | 无法表达真实意图 | 允许用户自定义描述，依据研究迭代而非一次做全 |
| 把“图片事实”误当“用户意图” | 生成结果照搬参考图 | 增加选择、确认、排除和角色分配步骤 |
| 自动分析消耗额度过快 | 200 次项目额度不足 | 保存不自动分析；用户确认后调用；编译不调用模型 |
| 浏览器本地数据被清除 | 意图历史丢失 | V2 明确本地边界；V3 再评估导出和同步 |
| 多图信息冲突 | Prompt 自相矛盾 | V3 显式提示冲突并要求用户决策 |
| 对比评估产生伪精确分数 | 用户错误信任 | 首版采用分档判断和证据，不使用未经标定总分 |
| 功能膨胀成建筑全过程平台 | 单人项目无法交付 | 严格按 V2、V3、V4 Gate 推进 |
| 只为作品集包装、没有真实验证 | 面试可信度不足 | 记录真实基线、失败、用户反馈与取舍证据 |

## 17. 跨行业迁移：能力抽象，不是当前范围

ArchBuddy 的可迁移能力不是“建筑知识本身”，而是以下通用链路：

| ArchBuddy 能力 | 通用 AI 产品能力 |
| --- | --- |
| 理解建筑参考图 | 多模态理解 |
| 拆分体量、材料、光线等 | 非结构化信息结构化 |
| 参考图与项目归档 | AI 分类、标签与知识资产化 |
| 多图分工组合 | 多源信息融合 |
| 模块化设计意图 | 生成式 AI 可控性 |
| 参考与结果比较 | AI 结果评估 |
| 局部调整再生成 | Human-in-the-loop 反馈优化 |

同一框架可以迁移到：

- 营销：构图、文案、人物、产品露出、CTA、品牌调性。
- 电商：主体、背景、灯光、卖点、使用场景与产品一致性。
- UI/UX：布局、组件、字体层级、颜色与交互模式。
- 视频：Hook、叙事、镜头、节奏、字幕、BGM 与 CTA。
- 企业知识：文档理解、信息结构化、知识组合、生成与检查。

产品策略仍是先在建筑场景做深：建筑师的专业 Schema 与真实工作流是首个验证场，而不是限制产品思考的边界。

## 18. AIPM 作品集应保留的证据

本项目应展示的不只是最终页面，还包括：

1. 用户工作流：为什么参考搜集与 AI 表达之间存在断层。
2. 产品取舍：为什么不做建筑全过程平台，先做 V2。
3. AI 能力边界：多模态理解、结构化输出、编译与评估分别承担什么。
4. Schema 演进：字段如何从建筑师语言与用户测试中产生。
5. Human-in-the-loop：AI 建议、用户确认、锁定与覆盖规则。
6. 评测设计：不仅看模型是否返回内容，还看证据、幻觉和用户保留率。
7. 可控性闭环：如何从“结果不好”定位到具体模块并修正。
8. 真实约束：额度、冷启动、隐私、权限、商店审核与失败案例。
9. 跨行业抽象：垂直问题如何归纳为通用 AI 工作流。

## 19. 待确认问题

进入交互设计与技术方案前需要确认：

1. V2 是否仍沿用固定“保持待修改原图视角与构图”的整体生成准则，还是允许用户切换目标模式。
2. V2 的结构化模块中，“空间与体量”“立面与构件”是否需要按建筑、室内、景观动态变化。
3. 最近意图历史的本地保存数量与删除方式。
4. 是否在 V2 支持导出/导入结构化意图 JSON，作为本地备份与作品集证据。
5. AI 分析后是否默认全部模块启用，还是要求用户主动确认后才进入 Prompt。
6. **已确认**：完整素材管理使用插件打开的本地网页页面，侧栏保留即时任务；先共享浏览器本地数据，云同步和桌面客户端后续按真实需求单独立项。
7. V4 对比时以结构化设计意图为主，还是同时允许选择原始参考图作为视觉证据。
8. 正式行为数据采集是否立项；若立项，必须先完成同意、最小化、保留期和删除机制。
