## 1. 可以直接讲的项目介绍

### 30 秒开场

我做的 ArchBuddy 面向方案研究和效果表达阶段的建筑设计师。它源于三个连续的工作问题：参考图保存繁琐、积累后难找回、找到之后还要重新写 AI 提示词。我把采集、视觉描述与检索、可编辑提示词、效果纠偏和版本保存串成一个工作流。核心取舍是让 AI 帮助理解和起稿，让设计师保留最终判断。目前核心能力已经完成开发和本人验收，外部用户的效率与检索质量仍需要对照任务验证。

### 约 2 分钟完整介绍

我自己是建筑设计师，做这个项目的起点来自工作经历，以及与几位设计师的探索性交流。浏览案例时，逐张保存和命名图片会打断思路；积累的素材后来很难找回；即使找到了参考图，还需要重新把视觉感受翻译成 AI 能理解的提示词。

因此，我把问题整理成一条连续工作流：采集参考图、整理与找回、表达设计意图、检查生成偏差、保存可复用的版本。

第一版先解决图片采集和单图提示词反推。随后我发现，参考图里的全部内容并不等于用户想要的设计目标，于是把整段输出拆成体量、立面、材料、构图、光线等可编辑维度，支持最多三张参考图组合，由设计师选择并确认。

针对生成结果不符合预期的问题，我们又加入效果评估：用户把外部工具生成的图片导回，系统对照已确认的提示词逐维度指出偏差，用户修改后保存新版本。为了让这些成果能持续复用，后续增加了完整图词库、视觉描述和自然语言检索。

技术上，我把模型与规则的职责分开：模型负责视觉理解、语义表达和偏差评估；Prompt 组装、版本管理和额度控制由代码负责。资产与向量索引主要保存在浏览器本地，云端提供模型调用。

我的重点是行业问题识别、工作流定义、需求排序、AI 与人工的分工，以及根据实际使用反馈做取舍。项目实现借助 AI 开发工具协作。当前已完成核心流程开发和本人验收，下一步要通过其他设计师的真实任务，验证找图、起稿效率和单位任务成本。

## 2. 用户背景、产品定位与价值

### 目标用户与问题来源

主要面向建筑设计师在方案研究、参考搜集和效果表达阶段的需求，兼顾室内与景观参考场景。问题来自项目所有者的行业经历与几位设计师的探索性交流。

已有交流记录中的典型反馈包括：

- 逐张保存、命名图片会打断找灵感的过程。
- 曾用 Notion 或印象笔记整理图片，后来依赖旧关键词找图，找不到时逐渐闲置。
- AI 出效果图前需要一个可试用的 Prompt 初稿，每次从零写很费劲。

准确交流人数、样本构成、逐字稿与操作耗时没有系统记录，不能表述为正式大样本用户研究。

### 核心价值假设

把散落的参考图变成可找回、可编辑、可复用的设计参考资产，减少“重新找图、重新表达、重新开始”的工作。

完整路径：

**采集／导入 → 项目归档与视觉描述 → 找回素材 → 结构化设计意图 → 人工确认 Prompt → 外部生图 → 偏差评估 → 新版本入库。**

### 产品边界

- Chrome 侧栏：当前网页或当前图片的即时任务。
- 插件内完整图词库：图片浏览、项目整理、检索、Prompt 与版本管理。
- ArchBuddy AI 服务：视觉理解、效果评估与文本向量计算。
- 图像生成由外部工具完成；插件本身不生成、放大图片。“4K”是输出给生图工具的文字目标，不是插件已实现的分辨率能力。
- 当前不包含云端素材同步、团队协作、独立桌面客户端或 CAD/BIM 理解。相关能力应由真实需求另行触发。

## 3. 迭代与关键产品决策

以下按实际演进梳理；早期 PRD 的版本编号与后来交付顺序不完全一致，以最新进度交接为准。

| 演进 | 要解决的问题 | 决策及原因 |
| --- | --- | --- |
| 采集与单图反推 | 保存参考图后仍要重新描述 | 连接图片采集与 Prompt 初稿 |
| 整段文本变成结构化维度 | 用户只想借鉴部分特征，全文重写难控制 | 按设计维度编辑，局部加入、替换与移除 |
| 单图扩展到最多三图组合 | 材料、体量、光线可能来自不同参考 | 分图分析、由用户组合，保留各自进度与错误状态 |
| 增加效果评估和版本 | 出图不满意，却难说清哪里偏了 | 对照确认目标逐项说明偏差，修改后形成新版本 |
| 侧栏扩展为完整图词库 | 大量素材浏览与长期整理不适合窄侧栏 | 即时任务与资产管理分界面承载，共享本地数据 |
| 关键词扩展为混合检索 | 文件名与旧标签不能覆盖视觉意图 | 补视觉描述，关键词即时响应，主动提交后补向量结果 |
| 补齐批量描述、进度和恢复 | 旧素材缺描述，逐张处理慢，中断状态不清楚 | 显式批量任务、有限并发、失败定位与进度记录 |
| 保存全部确认版本，侧栏只展示最近五份 | 近期工作入口与长期资产保留需求不同 | 展示数量与存储数量分开，避免旧成果自动丢失 |

这些选择的价值需要通过任务数据验证，功能变化本身不等于效率提升。

## 4. AI 技术架构与决策

### 4.1 模型与规则的职责

| 任务 | 当前方式 | 选择原因 |
| --- | --- | --- |
| 理解参考图、描述视觉特征 | 视觉模型 | 处理体量、材料、构图等非结构化信息 |
| 组装已选择的 Prompt 模块 | 本地规则 | 忠实保留用户选择，不在每次编辑时重新生成全文 |
| 语义检索 | 文本 Embedding＋本地相似度计算 | 复用资产向量，减少重复分析 |
| 生成图与目标的对照 | 视觉模型逐维度评估 | 提示视觉表现与文字目标的差异 |
| 分类、版本、删除、额度 | 程序逻辑 | 行为应明确、可复现 |

面试可讲：“我先识别哪些任务需要模型理解，哪些任务必须由规则保证。用户只修改材料时，其他模块不应被模型顺带重写。”

当前属于固定 AI 工作流，没有自主规划与工具选择机制，不宜称为自主 Agent。

### 4.2 领域适配与模型选型

当前使用现成视觉模型，通过建筑领域模块、证据要求和输出校验适配业务，没有训练专用模型或进行微调。

模型需区分“可见事实、合理推断、无法确认”。例如“灰色、粗糙纹理”可以来自图像观察，但具体材料品牌、建筑用途或项目背景不能凭外观确定。

代码中的视觉适配采用 DeepSeek 接口；产品短名称为 deepseek-flash，官方端点在代码中映射到 deepseek-v4-flash-vision-exp。实际运行可由服务配置覆盖，不应仅凭产品短名称判断真实调用型号。文本向量使用 TokenHub 的 kinfra-text-embedding-0.6b，当前约定 1024 维。

已验证的是当前方案可用；没有完整的多模型同题横评，不能宣称所选模型准确率最高或性价比最优。后续模型比较应同时看领域事实、结构稳定性、延迟与成本。

### 4.3 输出契约与程序校验

参考图分析采用固定标题与字段的文本，再解析成模块；缺失内容标记未知，有效模块过少则报错。效果评估使用 JSON，校验模块集合、重复项与状态是否合法。

“接口成功返回”不等于“业务结果可用”。程序能检查结构，却不能证明材料判断正确；模型自报的高置信度也不是经过校准的准确率。

### 4.4 当前三条计算链路

**参考理解：**图片 → 视觉模型 → 建筑维度与证据 → 用户编辑选择 → 本地规则组装 Prompt。

**效果评估：**生成图＋已确认 Prompt → 视觉模型逐维度比较 → 偏差说明 → 用户确认新版本。

**检索：**图片 → 视觉描述＋项目文字 → 文本向量 → 本地索引；查询 → 查询向量 → 本地相似度排序 → 合并关键词结果。

### 4.5 为什么用图片描述转文本向量

当前没有采用图片直接进入图文共同向量空间的检索方式，而是通过可阅读的视觉描述间接检索图片。

- 描述同时服务用户阅读与检索，可以复用已有视觉能力。
- 描述有误时，用户可以编辑并更新索引。
- 素材文本不变时复用向量；索引完整且有效时，搜索只需要生成一次查询向量。

代价：描述漏掉的视觉特征，后续文本向量无法凭空补回。“已有向量”并不代表图片内容已经被理解；只有文件名与分类的索引，视觉召回能力有限。

当前是案例语义检索，没有检索后自动生成答案的阶段，不必称为完整 RAG。

### 4.6 人工确认与评估边界

效果评估以用户确认的 Prompt 为目标，而非默认要求生成图复制参考图，因为用户可能只借鉴材料而不借鉴构图。

使用“符合、部分符合、明显偏差、无法判断”及简短证据，避免未经标定的总分。模型是偏差定位助手，设计师决定是否修改。模型评估本身仍需人工样本校准。

### 4.7 数据、性能与成本

- 小型结构化数据主要在 chrome.storage.local；图片 Blob 与向量索引在扩展 IndexedDB；未确认工作状态使用会话存储。
- 下载原图在电脑下载目录，插件可能只保存预览；导入图片保存扩展内副本，源文件不移动。不能把预览称为完整原图。
- 资产本地保存不等于全程离线：经用户同意，图片或索引文字仍需发送给对应 AI 服务。
- 密钥留在服务端。CloudBase 中资源固定归属 ArchBuddy 与运行阶段，不把共享环境视为本项目独占；命名前缀本身不等于权限隔离完成。
- 当前按匿名安装每日 20 次、项目每日 200 次控制调用；匿名安装不等于实名用户，次数限额也不等于精确金额预算。
- Prompt 编辑与组装不调用模型；向量按文本变化增量更新，相同文本可复用；导入不默认触发整库视觉分析。
- 开启图库 AI 后，新采集图可自动描述；旧图与导入图的缺失描述通过显式任务补齐。
- 描述使用有限并发、任务进度和失败状态。早期冷启动曾导致等待问题，后续调整超时；历史时长不能作为当前性能承诺。
- 卸载或浏览器数据清除可能造成资产丢失；备份、跨端同步、长期容量是后续需求。
- 首次索引、描述与查询竞争调用额度，仍需分任务记录真实 Token、耗时和重试，再决定预算分配。

## 5. 反推质量：如何用评测优化系统提示词

本节是拟补齐的评测闭环，不代表已取得前后对照成绩。它评估“系统分析参考图和生成 Prompt 初稿的质量”，与产品里的效果图评估功能分开。

| 维度 | 如何判断 | 对应优化 |
| --- | --- | --- |
| 结构稳定性 | 模块和字段可解析、无重复与异常缺失 | 输出契约、字段定义与解析规则 |
| 事实准确性 | 描述是否有视觉证据，是否编造功能或材料 | 事实／推断分离、未知状态、禁止臆测 |
| 关键特征覆盖 | 重要体量、立面、视角等是否被识别 | 观察优先级、模块粒度、示例 |
| 重复运行稳定性 | 同图多次运行的关键事实是否矛盾 | 消除模糊指令，在固定模型与参数下比较 |
| 用户可用性 | 可保留内容、错误修正与理解负担 | 精简空泛内容、调整模块边界 |

用户编辑应区分“纠正错误”和“主动改变设计意图”：把误认的玻璃改成金属是纠错；把白色改成红色可能只是新的设计要求，不能都算作模型错误。

建议执行：

1. 固定一批覆盖不同场景与困难情况的参考图，由设计师先标注关键事实及不可判断项。
2. 比较新旧系统提示词，保持图片处理、模型与参数一致，每图重复运行几次。
3. 按事实错误、遗漏、重复、格式异常等分类；一次聚焦一类问题。
4. 保留未参与调优的样本用于复核，避免只对熟悉案例有效。
5. 同时记录质量、延迟和成本；人工抽查优先，模型辅助评分须先与人工校准。
6. 对每轮保存“问题样本 → 原因假设 → 修改内容 → 前后结果 → 保留或回退”。

假设案例：模型常把灰色粗糙表面直接认成某种确定材料，可要求先描述颜色、纹理和反射，再谨慎判断材料类别。用同样本检查错误是否减少。此例说明方法，不是已有实验结论。

下游生图可以做补充评测，但应固定生图工具、版本和参数，考虑随机性，不能把生成器波动全部归因于反推 Prompt。精确复原参考图的原始提示词也不是可保证的目标。

## 6. 检索质量：召回、融合与重排

### 6.1 先定位失败环节

示例查询：“暖色砖立面、围合庭院、不要玻璃幕墙。”

| 现象 | 优先检查 |
| --- | --- |
| 描述没有庭院或砖立面 | 视觉描述覆盖与正确性 |
| 描述已更新，搜索仍按旧内容 | 索引指纹与版本一致性 |
| 描述正确，同义表达找不到 | Embedding 表达、查询、候选数量与阈值 |
| 目标进入候选但排得很后 | 融合排序、重排 |
| 排除条件经常被忽略 | 有证据的约束字段、过滤或重排；不能凭空推断 |
| 图库没有相关图仍返回貌似相关结果 | 无结果识别与阈值校准 |

当前已实现：视觉描述、关键词与向量混合检索、按文本指纹更新向量、相同文本复用、删除时清理索引。以上机制不能直接等同于已测得召回提升。

### 6.2 当前检索的具体限制

- 本地逐条计算余弦相似度，没有近似索引带来的搜索误差；优先改描述、表示与排序，无需先更换向量数据库。
- 关键词结果排在前面，语义候选去重后追加；宽泛关键词可能挤占前排。
- 向量相似度使用 0.35 阈值；候选上限随图库规模计算，限制在 12—40 之间，实际结果还受阈值影响。这些是代码参数，尚无完整数据证明最优。
- 当前关键词实现是自定义文字匹配与计分，不是 BM25；当前也没有接入 RRF 或专用重排模型。

### 6.3 优化顺序：先融合，再按证据考虑重排

**第一步：修正输入和索引。**先确保描述覆盖正确、向量对应当前文字；不让后续算法替缺失数据背锅。

**第二步：试验融合排序。**比较当前关键词优先合并与 RRF。RRF 按候选在两路列表中的名次形成统一排序，避免直接相加不同尺度的分数，不增加模型调用。参数仍需通过评测选择，不保证必然改善。

**第三步：必要时试验重排模型。**如果候选召回充分，但前几项仍不相关，可让 Cross-Encoder 等重排模型同时比较查询与候选描述。先召回 20—30 个候选再重排可作为实验起点，不能当作已确定最优配置。

重排会增加延迟与成本，不能找回候选集外的图片，也不能恢复描述漏掉的视觉事实。对于视觉细节缺失，应优先补描述或另行评估图文向量／视觉重排，而不是只换文本重排模型。新增云端重排还需明确数据发送、服务与额度边界。

### 6.4 对照评测

现有方案拟定 12 条预标查询、20 张描述抽样，可作为起点。查询覆盖精确词、同义改写、空间／材料组合、氛围、排除条件和无结果情况；图片与相关性需在看结果前标注。

同一批数据比较：

**仅关键词 → 仅向量 → 当前混合 → 融合排序 → 融合后重排。**

| 指标 | 解释 |
| --- | --- |
| Recall@K | 已标注相关图片中，有多少进入前 K 个候选 |
| Hit@3 | 有目标图的查询中，有多少在前三项命中至少一张 |
| Precision@3 | 前三项中有多少确实相关；报告应统一不足三项的计算口径 |
| 排除条件违反／无结果误报 | 不该出现的内容是否被错误返回 |
| 搜索耗时、请求与 Token 成本 | 质量增益是否值得额外等待与费用 |

只标一张目标图时先报告目标命中率，不能声称测得全部相关图片召回率。需要更细排序评价时再加入分级相关性与 nDCG。

只有在固定样本对照中观察到稳定收益，且延迟和成本可接受，才保留新方案；同时记录提升、退化与失败案例。

## 7. 可直接回答的 AI 技术追问

**你做了哪些 AI 技术判断？**

我把视觉理解与评估交给模型，把 Prompt 组装、版本和额度交给规则。领域适配通过建筑维度、证据要求和输出校验完成，没有做微调。检索用图片描述转文本向量，结合关键词在本地匹配；效果评估以用户确认目标为依据，最终修改由设计师决定。

**为什么不直接用通用聊天工具？**

我们的差异化假设是把网页采集、项目资产、可编辑设计维度和版本关联接通，减少重复搬运上下文。通用工具也能分析图片，因此需要任务对照证明连续工作流的实际价值，不能只靠功能列表。

**为什么不先做云图库或直接生图？**

先验证素材积累、找回与复用是否成立，复用用户现有生图工具，控制账户、同步、存储和模型成本的范围。真实跨设备或团队需求出现后再立项。

**为什么不微调或上 Agent？**

当前核心问题先通过任务拆分、提示约束、数据结构与人工确认解决。尚无充足证据证明需要训练专用模型或自主规划；新增复杂度应对应明确失败模式。

**怎么让反推更稳定准确？**

已有固定模块、证据和未知状态、程序解析。下一步用固定样本比较结构、事实、覆盖及重复运行一致性，按错误类型迭代系统提示词，并保留未参与调优的样本复核。目前尚无完整前后提升数据。

**是否需要加重排？**

先判断目标图是否进入候选。未召回时检查描述、索引和候选策略；已召回但排得后，先改善两路融合，再比较重排的质量、延迟与成本。当前没有部署重排模型。

**你们用了 RAG 吗？**

当前实现是图片描述驱动的案例语义检索，包含向量化、检索与结果展示，没有检索后生成答案。它用到了与 RAG 检索层相通的方法，但不包装成完整 RAG 系统。
