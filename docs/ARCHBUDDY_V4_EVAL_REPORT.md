## 1. 产品问题与本轮要验证的判断

建筑设计师需要在“参考图收集 → 找回素材 → 形成提示词 → 检查生成结果 → 修改提示词”的连续工作中保留可复用资产。本轮验证三个判断：

1. 两级项目目录与词库分组能让设计师找回旧素材和旧方案，而不依赖记住文件名。
2. 图片核心描述能改善自然语言找图；输入中关键词即时反馈，回车后融合本地向量结果。
3. 设计师能保留对提示词的控制，评估只帮助定位偏差和生成下一版本；旧版本可追溯。

**评估原则**：先写测试任务与期望图，再看检索结果；同时记录成功与失败案例。按真实任务而非“模型看起来聪明”给分。参考 [OpenAI 官方 Eval 最佳实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices)关于任务专属样本、预定指标和人工校准的建议。本报告使用这些方法，不依赖 OpenAI Evals 服务。

## 3. 本次验收方式

### 环境与记录口径

- 在 Chrome 的 `chrome://extensions` 重新加载从本仓库 `extension/` 加载的本地版；关闭旧图词库标签后重新打开。此版与商店版扩展 ID 不同，数据空间不同。
- 本地开发模式临时指向 `http://127.0.0.1:8080`；服务保持运行。此模式只用于验收，提交或打包前恢复 `cloud`。当前 `process-test` 调用上限不是云端 20/200 每日额度。
- 用现有真实图库测试找图；导入、拖动、删除请另外准备**可丢弃**的小目录，避免破坏已有作品。每项记录：成功／失败、用时、实际表现、问题截图。AI 操作会产生模型调用。

签收门槛（本轮预先设定）：A1–A8 核心任务均能完成，无误删、丢失既有描述或提示词版本。视觉样式问题单独排队；阻断任务或造成数据错误的问题先修复再复测。

### B. 自然语言搜索 Eval

先由设计师**不看搜索结果**写下 12 条真实查询，并为每条指定至少一张“期望能找回”的图库图片 ID／文件名。建议覆盖：4 条精确词、4 条同义改写或空间/材质组合、2 条模糊氛围描述、2 条带排除条件或易混淆条件。若图库确实没有目标图，应标为“预期无结果”，不能按漏召回算。

每条记录两次结果：①仅输入文字、不按回车时的关键词前 3 项和首个可见结果时间；②按回车后前 3 项、首次稳定结果时间、状态提示。记录目标图是否进入前 3、是否出现明显错误图。检索逻辑当前先列关键词命中，再补语义候选；若宽泛关键词占满前排，应作为排序问题记录，而不能只凭“语义候选存在”判断通过。

| 指标 | 计算方法 | 目标／状态 |
| --- | --- | --- |
| Top-3 找回率 | 有目标图的查询中，目标进入前 3 的条数 ÷ 有目标图查询数 | 建议门槛 ≥ 75%；待实测 |
| 语义增益 | 同一批查询，回车后比关键词阶段多找回目标图的条数；同时记退化条数 | 目标为正增益且无明显退化；待实测 |
| 无关结果 | 设计师对前 3 项逐个标“相关／部分相关／无关” | 列出至少 3 个失败案例，供下一轮定向优化 |
| 失败回退 | 断开本地服务后输入关键词并回车 | 关键词结果仍可见，错误提示可理解；待实测 |

### C. 描述质量与性能

- 从导入图、下载图和不同项目类型中抽取 20 张（包含失败／模糊图）。设计师逐张标记：**可用于以后找图／需修改／明显错误**；另外标“主体、视角、材质、光线”四项中可见信息是否写准，是否编造图中看不出的地点或用途。给出具体错误例子。20 张是本轮小样本，不推断总体准确率。
- 记录图词库首次打开、同项目切换、打字筛选、回车混合搜索各 10 次的时长；区分冷启动与已建索引的暖启动。报告中写设备、Chrome 版本、图库张数、网络情况，分别报中位数和最慢一次。此轮**不预填性能数值**。
- 批量描述补齐时记录请求数、成功数、失败数、重试数、总用时、每分钟处理张数。现有界面没有完整 Token 台账：此项如无法从供应商返回或服务记录核实，报告保持“未知”；下轮再补用量记录能力。
- 如感觉卡顿，使用 Chrome DevTools 的 [Performance 面板](https://developer.chrome.com/docs/devtools/performance/overview)录制打开图库与搜索各一次，保存本机 trace 并记录主线程阻塞位置。该工具能记录 CPU 活动与交互轨迹，不能替代上面的用户任务计时。

## 5. 从结果到下一轮迭代

按“用户任务失败次数 × 影响程度 × 修复成本”排序，保留一页决策表：**现象 → 证据 → 原因假设 → 方案 → 新旧对比 → 是否保留**。优先处理找不到图、错删／丢数据、搜索明显卡顿；视觉排版集中到下一轮 UI。已知待验证假设：

1. 8 张旧下载图虽在图库中，但缺描述；先查它们为何没有进入描述目录，再补齐并更新索引。
2. 关键词命中排在语义结果前，可能压低语义改写的前 3 命中率；用 B 组查询证明后再调整融合排序。
3. 首次索引与常规查询共用额度，批量描述也消耗调用；需要实际 Token 与耗时数据后决定预算和发布节奏。
4. 本地浏览器存储没有跨设备备份；如用户有长期资产需求，下一轮先验证导出／备份价值，再评估云同步。

## 6. 面试材料建议

在这份 Eval 报告之外，准备四份可展示的证据：

1. **3 分钟演示**：一张真实参考图从采集、归类、自然语言找回、提示词编辑，到生成图评估与版本回看。演示使用可公开图片。
2. **一页产品决策图**：痛点、目标用户、插件侧栏＋全页图库＋AI 服务的分工；解释为何保留人工确认、为何先用本地向量索引、如何处理隐私与 20/200 额度。
3. **迭代对照**：挑“关键词搜索慢／召回差 → 即时关键词＋本地向量”“批量描述中断 → 状态恢复”“图片大图交互 → 系统看图”三个案例，写清用户反馈、取舍、验证和未解决处。没有前后可比实测数字就只讲机制变化和本轮实测。
4. **外部用户证据**：在本机验收后请 5–8 名建筑设计师独立做 A2、B 组找图和 A7，记录完成率、耗时、卡点与原话。招募未完成前明确说“计划”，不要称已验证。

面试高频追问应能回答：**问题从哪里来；为什么优先解决找回而非直接生图；如何定义语义搜索成功；为什么选本地索引；调用失败怎么回退；模型费用如何限制；数据存哪里；V3 已上线与 V4 本地验证如何区分；哪些数字是实测、哪些只是目标；作为产品负责人本人做了什么。**
