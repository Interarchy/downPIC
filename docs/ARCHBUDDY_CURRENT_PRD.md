# ArchBuddy 简版 PRD｜当前插件能力

> 更新：2026-09-28。用途：面试讲述与产品复盘。
>
> 发布状态：V3 已在 Chrome Web Store 上线并由项目所有者验收；图词库、自动描述和语义检索等后续功能已完成本地联调，尚未部署或更新商店。代码清单版本为 0.6.0，不代表商店版本。

## 1. 产品定位与问题

**一句话定位**：ArchBuddy 帮建筑设计师把网页参考图沉淀为可检索的视觉素材，再转成可编辑、可迭代的生图提示词。

主要用户是方案研究和效果表达阶段的建筑设计师，建筑可视化设计师是相邻用户。项目基于设计工作经验提出三个待验证问题：参考图保存后难找回和复用；一次生成的长提示词难以局部控制；效果图偏离预期时缺少明确的修改依据。这些问题尚未经过独立用户研究验证。

## 2. 核心流程

网页采集或导入本地项目文件夹 → 按类型与项目归档，形成可检索的素材 → 找回参考图 → 选择最多三张图，逐维度编辑并确认完整提示词 → 在外部工具生图 → 导回生成图，逐维度评估偏差 → 局部修改并保存新版本。

插件弹窗负责快速入口，侧栏负责当前图片的采集、提示词生成和效果优化；插件内完整网页负责图片和提示词的长期管理。Gemini、ChatGPT 仅提供跳转，生成图片由用户在外部工具完成。

## 3. 主要需求

| 模块 | 用户能完成的事 | 验收要点 | 状态 |
| --- | --- | --- | --- |

| 图词库 | 浏览图库和词库；导入本地文件夹并合并同名类型；跨类型拖动项目；查看预览、描述、提示词与版本 | 导入后原电脑文件保留；双击图片或点击详情图直接系统查看；导入图首次系统查看可能生成专用副本；项目归类持久化，删除范围明确 | 本地完成，待真实素材验收 |

## 4. 关键产品取舍

- **AI 给建议，设计师作决定**：模型负责描述、结构化和偏差提示；用户选择、编辑并整体确认后才形成可复制内容或新版本。
- **侧栏与完整页面分工**：网页浏览时快速操作；比较图片、管理项目和找回旧方案时使用完整图词库。
- **先验证语义找图的价值**：输入时本地即时匹配关键词；用户单独同意后，图片描述与提示词生成并更新本地向量，提交搜索只生成一次查询向量，在插件内合并排序。无需云端向量库，仍受现有额度约束；缺少描述的旧图片无法按视觉内容可靠召回。
- **本地保存与单独同意**：下载原图保存在用户电脑；文件夹导入会把支持的图片复制到扩展 IndexedDB，原文件保持原位。索引、预览、方案和版本主要在扩展本地。开启图库 AI 后才自动发送新下载图片的限宽预览生成描述；首次建索引和文本变化时才把对应文字发送给 TokenHub；每次搜索只发送查询。向量与图片保留在插件本地，模型密钥留在服务端。

## 5. 验证计划与当前证据

计划请 5–8 名目标设计师独立完成“采集→找回→生成提示词→评估”任务，记录完成率与卡点、自然语言搜索前 3 项的可用比例，以及旧素材和旧提示词的复用情况。**这些是拟验证指标，尚无真实用户结果。**

目前的证据是：V3 商店功能已由项目所有者验收；后续功能经过本地合成图片、真实模型调用和静态检查。真实设计素材的搜索满意度、系统图片程序窗口以及新接口部署后的云端链路仍待验证。跨设备同步、团队协作和插件内直接生图不在当前范围。

## 6. 面试时可用的 60 秒介绍

> 我从建筑设计师搜集参考图、写提示词和调整效果图的流程出发，做了 ArchBuddy。它用插件采集并按项目保存图片，图词库把图片与视觉描述沉淀下来，支持自然语言找回。用户选参考图后，AI 将视觉特征拆成设计师熟悉的维度，设计师可以编辑、组合最多三张图，再确认完整提示词。效果图由外部工具生成，导回后逐项检查与原意图的偏差，只修改相关部分并保留版本。产品重点解决素材难复用、AI 输出难控制、修改缺少依据三个问题。V3 已上线验收；图库和语义检索已本地跑通，下一步是用真实设计师任务验证检索质量和复用价值。

**可展开的追问**：为什么采用“插件侧栏＋完整图库＋AI 服务”；为什么保留人工确认；语义搜索如何控制调用成本和数据范围；如何区分已发布功能、本地验证与真实用户结果。
