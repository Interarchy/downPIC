## 每周如何分析

从仅本项目、仅development的两集合取得受控导出，保存为本地JSON；本轮汇总命令本身不连接云端，不读取默认账号，不提供批量跨项目导出。导出必须完整，且需明确其有效日期范围，不能凭文件中最早/最晚事件推断覆盖率。

输入结构为events、activities数组，以及coverage中的eventsFrom/eventsTo/activitiesFrom/activitiesTo。事件带固定projectId、stage、去标识actorHash与已验证字段；摘要带firstActiveDay、days的active/library布尔值、expiresAt和可选withdrawnAt。表内不存在图片、提示词、查询或路径。

```powershell
node cloudbase/scripts/metrics-report.mjs --input cloudbase/dist/analytics-verification-20261007/synthetic-export.json --from 2026-11-25 --to 2026-12-01 --as-of 2026-12-01 --cohort-from 2026-10-07 --cohort-to 2026-10-07
```

统计周和首次使用用户组可以独立选择；命令也支持--format json。先看漏斗，再看连续使用与成熟回访，最后结合搜索和AI质量定位问题。报告只提供观察结果，疑似原因仍需访谈或任务测评确认。

### 口径与已知限制

- 新构建首次点击参考图分析时建立一个逻辑任务；多张图、重试继续关联该任务。确认后实际剪贴板复制成功算完成。手动Ctrl+C备用复制、未开始分析的纯手工编辑不计入本次完成率，不能推断为失败。
- AI请求以独立随机请求ID关联；参考图、效果评估、查询向量、自动描述/索引分组。额度、无效输入、未配置、取消单列，避免把明确拦截当作普通能力请求失败。这里的成功率是客户端能力请求获得可用响应的比例，不等于模型真实推理次数或计费成功率；网络、授权失败可能未触及模型。耗时是插件端观测等待，包含会话换取与网络，不是纯模型计算时间。
- 只有主动入口、保存/导入、任务开始、确认、复制、复用与搜索提交更新活跃。AI后台行为和任务/搜索结果返回不额外算活跃，避免跨午夜完成制造连续使用。
- 参与统计的安装同意周期不是人数；重新同意、重装或更换浏览器会改变主体。到期后的首次活跃是新的观察期起点，不是人生首次安装。
- 摘要自首次收到起固定60天，不因持续使用延长。需要在Day56窗口完成后、摘要过期前生成去主体的结果快照；优先按首次使用日分析。七天用户组全部成熟时最早成员可能已过期，不能忽略后据剩余成员宣称完整组留存；使用每日快照合并总体分子/分母，或标记数据不足。摘要过期后不能恢复个体长期留存。
- 原始事件30天，较早任务若跨越很长时间才完成，开始事件可能已删除；周报只能在完整覆盖的有效窗口内解释漏斗。覆盖不完整标记未知，计数是文件中观察到的量，不补零。
- 本地最多200条，每批25条，5分钟周期发送，每条最多5次失败。只上报24小时内记录，过期项在插件下次运行或队列清理时删除；Chrome关闭期间不会自动执行清理。高频、断网、时钟误差、浏览器关闭或撤回会造成缺失。
- 在线撤回写入拒收状态；离线不能保证控制请求送达。历史数据保持原到期时间，提前删除需受控处理且限定本项目。没有精确使用时长、搜索相关性或用户满意度结论。

## 资源增量如何判断

不新增模型调用，不扣减或改动已确定的每日50/500业务额度；新增消耗来自统计HTTP请求、数据库与受控导出。批量发送减少HTTP次数，不把25条事件变成一次数据库写入。

按当前代码，每条新事件通常读取事件和摘要各一次；主动行为再写事件和摘要各一次，AI事件只写事件。重发命中只读取已有事件；撤回通常读写一份摘要。这是逻辑文档操作量，不能等同于CloudBase计费单元，事务重试和清理还有额外开销。

举例：每天100个参与统计的活跃安装，每安装20条事件，共2000条/天，通常约4000次文档读取、2000—4000次写入。30天原始事件约60000条，摘要最多覆盖60天内有效观察周期。HTTP批数取决于各安装各5分钟窗口的事件分布，稀疏使用会接近逐事件发送；每个非空发送周期另查一次状态。真实套餐、账单与保留机制验证后再判断是否升配，本轮未声称需购买某档套餐。
