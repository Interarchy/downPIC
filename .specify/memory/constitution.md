# ArchBuddy MVP 项目章程

## Core Principles

### I. 核心路径优先

每个版本 MUST 优先实现已经确认的核心用户路径，并以该路径能完整演示为首要目标。
需求排序 MUST 服从当前 Spec 中的优先级；非核心功能、锦上添花的交互和未确认需求
MUST NOT 阻塞 MVP 交付。实现选择应以最快形成可用闭环为准，而不是追求完整平台能力。

理由：本项目是复杂产品的 MVP 演示实现，价值在于证明核心产品逻辑成立。

### II. 最小改动实现

开发 MUST 优先复用现有目录、组件、数据结构和已验证流程，只修改完成当前需求所必需的
代码。MUST NOT 因为局部功能顺带重构无关模块，也不得把尚未提出的需求纳入本次实现。
当存在多种可行方案时，MUST 选择改动范围更小、依赖更少、容易静态检查的方案。

理由：最小改动能够降低回归风险，并缩短从规格到可演示结果的时间。

### III. 拒绝过度设计

本阶段 MUST NOT 为假设中的未来需求增加抽象层、插件机制、通用框架、复杂配置、
多阶段兼容层或提前优化。无需考虑横向扩展、长期可扩展性或通用化复用；只有当前需求
明确要求的状态、接口和异常路径才进入实现。防御性处理 MUST 限于核心路径会实际遇到
且会阻断演示的问题。

理由：过度抽象会增加理解、修改和审查成本，偏离 MVP 验证目标。

### IV. 静态检查即质量门槛

本阶段的唯一强制质量门槛是与改动相关的静态代码检查。实现完成后 MUST 运行仓库已有的
语法检查、类型检查、Lint、清单或构建配置检查中适用的项目，并修复发现的问题。
MUST NOT 为本阶段新增单元测试、集成测试、端到端测试或测试框架；测试编写和测试覆盖率
不作为交付条件。若仓库没有对应静态检查，MUST 通过代码审阅和最小的解析或构建检查
确认改动没有明显语法和配置错误。

理由：当前目标是快速完成可信的 MVP 演示，而不是建立生产级测试体系。

### V. 中文文档与决策可追溯

所有新建或更新的产品文档、规格、计划、任务、验收说明和交付总结 MUST 使用中文。
代码标识符、标准协议名、第三方产品名和必须保持原样的命令可以使用英文。关键范围取舍、
用户确认、已知限制和未完成项 MUST 写入对应文档，不得只存在于对话中。

理由：统一语言并保留决策依据，便于非技术背景的项目所有者理解和复核。

## MVP 范围与安全底线

- 本项目是 ArchBuddy 的 MVP 演示实现，不以生产级可扩展性、完整监控、高可用、
  自动化测试覆盖或长期架构演进为目标。
- 本阶段 MUST NOT 把无障碍适配、键盘完整可达性、屏幕阅读器支持或无障碍验收
  纳入需求、计划、任务或完成门槛，除非用户以后明确修改本章程。
- 快速交付不得削弱密钥安全、用户明确同意、数据最小化和现有隐私承诺。
  密钥、令牌和环境凭据 MUST NOT 写入仓库或前端产物。
- CloudBase 是多项目共享环境。任何云端方案或变更 MUST 限定在
  `projectId=archbuddy`、明确阶段和已登记资源内，不得读取、覆盖、清理或复用
  其他项目的数据、身份、日志、密钥、统计、额度或预算。
- 涉及新增云端资源、持久化数据、行为统计或部署时，MUST 先遵循
  `docs/CLOUDBASE_PROJECT_ISOLATION.md` 完成资源登记和边界核对。
  纯本地开发不得声称云端隔离、部署或运行验证已经完成。
- 用户已经确认的匿名额度边界仍为每个匿名安装每日 20 次、整个 ArchBuddy 每日
  200 次；常规用户界面不得显示具体剩余额度。

## 开发流程与完成标准

1. 开始任务前 MUST 检查当前目录、`direction/plugin` 分支、已有改动、
   `AGENTS.md` 和 CloudBase 隔离文档，保护用户已有工作。
2. 规格与计划 MUST 先标出核心路径、明确范围外事项，并删除测试、无障碍、
   扩展性和非必要防御性工作的默认任务。
3. 实现 MUST 按核心路径的依赖顺序推进；遇到不会改变产品行为的小型技术选择时，
   直接采用最简单方案，不追加产品澄清。
4. 完成条件仅包括：核心路径代码已实现、相关静态检查通过、没有提交密钥或敏感数据、
   文档和已知限制已同步。自动化测试、性能压测、无障碍检查和生产级可观测性
   不属于默认完成条件。
5. 若某项安全或 CloudBase 隔离要求与快速实现发生冲突，MUST 保留安全与隔离底线，
   并缩小功能范围；不得用“MVP”作为跨项目访问、泄露凭据或扩大数据收集的理由。
6. 每次交付总结 MUST 简要列出修改内容、执行的静态检查、未验证项和下一步，
   不得把未运行的检查或未部署的资源描述为已完成。

## Governance

本章程约束后续 Spec Kit 的规格、计划、任务与实现流程。功能文档与本章程冲突时，
流程和质量门槛以本章程为准；`AGENTS.md`、
`docs/CLOUDBASE_PROJECT_ISOLATION.md` 和隐私政策中的安全边界仍然有效，
且不得被本章程中的快速交付原则削弱。

章程修改 MUST 由用户明确提出或确认，并在文件顶部的 Sync Impact Report 中记录影响。
版本采用语义化规则：删除或反转既有治理原则为 MAJOR，新增原则或实质扩展约束为 MINOR，
不改变含义的澄清为 PATCH。首次正式章程版本为 1.0.0。

每份实施计划 MUST 在开始开发前完成章程符合性检查。任何例外 MUST 写明原因、影响范围
和用户确认；未获得确认的例外不得进入实现。提交前 MUST 移除顶部临时
Sync Impact Report，并保留版本号与修订日期作为正式记录。
